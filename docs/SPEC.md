# Taskforge: project specification

## 1. Overview

**Taskforge** is a project management and time tracking app for developers: projects, a Kanban
board, work-session timers and productivity analytics. It is a portfolio project, built to
show backend engineering, database design, authorization, API design, testing, Docker and
deployment, in a product that is actually usable rather than a CRUD tutorial.

### Goals

- A usable, responsive, accessible application.
- An architecture that is easy to follow and maintain.
- The same Docker workflow on Windows and Linux, with nothing but Docker needed on the host.
- Free hosting: Vercel for the app, Turso for the database.
- Desktop installers for Windows and Linux.
- Setup, architecture, tests and deployment documented in the repository.
- Built in milestones, with the app runnable after each one.

## 2. Technology stack

| Part | Choice |
|---|---|
| Framework | Nuxt 4: Vue 3 and TypeScript for pages, Nuxt server routes (Nitro) for the backend |
| UI | Nuxt UI 4 (Tailwind CSS 4): dashboard layout, forms, modals, dark mode |
| Database | SQLite through libSQL: a local file in development, Docker and tests; Turso in production |
| ORM and migrations | Drizzle ORM, with SQL migrations generated by drizzle-kit |
| Sign-in | nuxt-auth-utils: encrypted cookie sessions, password hashing |
| Validation | Zod schemas, shared by forms and server routes |
| Kanban | vue-draggable-plus, plus a keyboard "Move to…" menu; the server validates every move |
| Charts | Chart.js through vue-chartjs |
| Security | nuxt-security: a strict Content Security Policy with per-request nonces, security headers |
| Tests | Vitest (unit and server tests against a throwaway SQLite database), Playwright (browser flows) |
| CI | GitHub Actions: lint, type check, tests, production build, Docker image smoke test |
| Hosting | Vercel (connected to the GitHub repository) with Turso |
| Desktop | Tauri 2 installers built in GitHub Actions |

Add packages only when they solve a concrete need, and check current versions and
compatibility rather than assuming them.

## 3. Features

### 3.1 Access and account security

- **Demo access:** "Try the demo" creates a private workspace seeded with realistic data, with
  no password. Demo workspaces expire after a few days and are then deleted.
- **Registration and sign-in** exist in the code, but registration is switched off in
  production by a setting.
- Validate all input on the server.
- Protect signed-in routes with server middleware.
- Check ownership on every project, task and session, so changing an id in a URL never exposes
  or changes another user's data.
- Rate-limit sign-in and demo creation. Store the limits in the database, not in memory,
  because serverless instances don't share memory.
- Keep secrets out of source control.

### 3.2 Dashboard

Real metrics from database records:

- active projects;
- tasks completed in a chosen period;
- overdue tasks;
- total tracked time;
- a weekly task completion chart;
- recent activity;
- upcoming deadlines;
- project progress.

No hardcoded numbers. Every panel has a useful empty state.

### 3.3 Projects

- Create, view, edit, archive and delete projects.
- Fields: name, description, start date, deadline, priority and status.
- Progress is based on task completion.
- A project page shows its tasks and recent activity.
- Statuses: Planning, In Progress, Completed, Archived. Priorities: Low, Medium, High.
- Members and roles are optional, for later, if collaboration is added.

### 3.4 Tasks and Kanban

- Columns: Backlog, To Do, In Progress, Done.
- Each task has:
  - a title and description;
  - status and priority;
  - a due date and an assignee;
  - tags and comments;
  - an estimated effort and its actual tracked time.
- Drag-and-drop comes only after the task update route and its authorization are tested. The
  server validates every status transition.
- Marking a task Done records a completion time; reopening it clears that time.

### 3.5 Work-session timer

- Start and stop a timer on a task.
- Store each session's user, task, start and end. The server computes the duration and never
  trusts one sent by the browser.
- A user can have only one running timer, enforced by a database constraint as well as the code.
- Check ownership before starting or stopping a session.
- Store times in UTC and display them in the user's timezone.

### 3.6 Analytics

Date-filtered charts and summaries:

- tasks completed per day;
- tracked hours per week;
- estimated versus actual time;
- task counts by status;
- project progress over time.

Use SQL aggregation rather than loading every record into memory. Validate date ranges and
handle empty data.

### 3.7 Activity history

- Record important actions: project creation, task status changes, task completion.
- Show recent activity for the current user's projects.
- Notifications are optional. Background jobs are added only for a concrete need, with how they
  run documented.

### 3.8 REST API

- A small, documented API under `/api/v1` for projects and tasks.
- Personal access tokens, stored hashed.
- Validated requests and consistent status codes and error bodies.
- Tests for unauthenticated and unauthorized requests.

### 3.9 Desktop app

- A Tauri shell around the hosted app, for Windows (`.msi` and `.exe`) and Linux (`.deb` and
  `.AppImage`).
- Native extras: the running timer in the system tray, notifications, and a global shortcut.
- Built in GitHub Actions and linked from a download page on the site.

## 4. Database design

| Table | Purpose |
|---|---|
| `users` | Accounts: demo or registered |
| `projects` | Projects and their owner |
| `tasks` | Tasks belonging to projects |
| `task_comments` | Task discussions |
| `tags`, `task_tags` | Reusable labels and their many-to-many link to tasks |
| `work_sessions` | Tracked work periods |
| `activity_logs` | Important actions |
| `api_tokens` | Hashed personal access tokens |
| `rate_limits` | Request counters for sign-in and demo creation |

### Rules

- Foreign keys are on (`PRAGMA foreign_keys = ON`). Cascade and restrict behavior is chosen
  deliberately for each relation.
- Index the frequent filters: project, status, assignee, due date and session owner.
- Use CHECK constraints and unique indexes to enforce invariants in the database.
- Store timestamps as Unix seconds, in UTC.
- Use transactions for multi-step writes.
- Avoid redundant stored values unless there is a clear reason.
- Generate demo data with a seeding module, not hardcoded responses.
- Keep analytics queries efficient and tested.

```text
User
 ├── Projects (owner)
 ├── Assigned tasks
 ├── Work sessions
 └── API tokens

Project
 └── Tasks
      ├── Comments
      ├── Tags
      └── Work sessions
```

## 5. UI and UX

- A responsive layout with a sidebar and top bar, for desktop, tablet and mobile.
- Clear typography and consistent spacing.
- Metric cards, project cards with progress, and Kanban columns with task cards.
- Accessible forms with validation messages.
- Loading, empty, error and success states.
- Keyboard-accessible controls and sufficient color contrast.
- No mock data once real data exists.

## 6. Docker

The app runs locally with Docker Compose. There is no database container: SQLite is a file.

- **`app` service:** the production build in one Node 24 container.
  - Runs as a non-root user.
  - Has a health check on `/api/health`.
  - Applies migrations on start. This is safe because applied migrations are skipped and the
    container is SQLite's only writer.
  - Keeps the database on a named volume.
  - Port set by `APP_PORT` (default 8094).
- **`dev` service** (profile `dev`): live reload with the source mounted, and every npm
  command (lint, typecheck, tests, migrations).

### Requirements

- Install dependencies reproducibly from the lockfile, in a multi-stage build.
- Exclude `.env`, Git data, local dependencies and logs with `.dockerignore`.
- Never bake credentials into the image.
- Never delete the database volume on a normal shutdown. Document resetting data separately,
  with a warning.

### Windows and Linux

- **Windows:** Docker Desktop with the WSL 2 backend. Cloning inside the WSL filesystem is
  faster; a Windows folder also works, with file-watch polling.
- **Linux:** Docker Engine with the Compose plugin.
- Use only standard Compose features, and Linux-style container paths, with no host paths.
- Give each host command in both PowerShell and Bash.
- `.gitattributes` keeps text files LF.
- Respect case-sensitive file names.
- Test on each platform where possible, and state plainly what wasn't tested.

## 7. Deployment (Vercel and Turso)

1. Push the source to GitHub.
2. Create a Turso database on the free plan, and an auth token for it.
3. Import the repository into Vercel, which builds Nuxt on each push.
4. Set `NUXT_DATABASE_URL` and `NUXT_DATABASE_AUTH_TOKEN`, plus the session secret, in Vercel.
5. Run migrations as part of the build, with the same script used everywhere else.
6. Deploy and check the logs.
7. Test demo access, authorization, CRUD flows, analytics and persistence.
8. Confirm no credentials appear in the repository, logs or browser output.
9. Document redeploys, migrations, rollback and troubleshooting.

Check current Vercel and Turso plan limits before relying on them.

## 8. Roadmap

Each phase ends with the app runnable and its tests passing.

1. **Foundation:** Nuxt, SQLite and migrations, Docker, health check, CI, README.
   - *Done when* a fresh checkout starts with the documented commands on Windows and Linux, and
     the app reaches its database.
2. **Demo access and the app shell:** demo workspaces and their expiry, registration behind a
   setting, sessions, rate limits, the responsive layout.
   - *Done when* visitors get a private workspace and can't reach anyone else's data.
3. **Projects:** schema, routes, ownership checks, pages, seed data.
   - *Done when* project CRUD works with server-side validation and authorization tests.
4. **Tasks and Kanban:** tasks, tags and comments, filters, status changes, the board and the
   keyboard "Move to…" menu, completion times.
   - *Done when* task operations persist, enforce access and are covered by tests.
5. **Timer and analytics:** the session lifecycle and its safeguards, dashboard queries, charts,
   date filters.
   - *Done when* times are computed on the server and analytics use real data.
6. **API:** `/api/v1` endpoints, tokens, validation, tests, documentation.
   - *Done when* the documentation matches the behavior and unauthorized requests are rejected.
7. **Hardening:** CSP and headers, validation and error review, edge-case tests, index review,
   Lighthouse.
   - *Done when* the production build passes all tests and audits.
8. **Vercel and Turso:** deployment, environment variables, migrations, verification.
   - *Done when* the public app works over HTTPS with no secrets exposed.
9. **Desktop installers:** the Tauri shell, tray timer, notifications, shortcut, CI builds,
   download page.
   - *Done when* the installers install and run on Windows and Linux.
10. **Polish:** screenshots, README and architecture notes, API examples, the portfolio entry,
    optionally a PWA.

## 9. Testing

Write tests alongside each feature, covering:

- demo access, sign-in and guest access;
- project CRUD and authorization;
- task CRUD, status transitions and assignment;
- cross-user and cross-project access attempts;
- timer start and stop, and duplicate running timers;
- date filtering and analytics calculations;
- API authentication and validation;
- database constraints and edge cases.

Run the tests in Docker with `docker compose run --rm dev npm test`. A feature counts as tested
only when its tests exist and pass.
